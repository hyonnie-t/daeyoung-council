# Firebase 보안 적용 절차

`database.rules.json`은 2026-10-06 콘솔에 게시했다(효니 확인). 아래 순서는 규칙을 다시 바꾸거나 다른 프로젝트에 적용할 때의 기록이다. 앱 코드(익명 인증)를 먼저 배포하고 나서 규칙을 바꿔야 하고, 순서가 바뀌면 앱이 멈춘다. 루트의 숫자 키(`1001`…)는 옛 가져오기 데이터로 규칙에 없어 앱에서 접근이 막히지만 콘솔에는 남아 있다(앱은 `tasks/`만 쓴다).

## 순서
1. **백업**: `FB_API_KEY=웹API키 node tools/backup.mjs` (Node 18+). 규칙을 바꾸기 전 `backup/`에 JSON이 생기는지 확인. 현재 콘솔 규칙 JSON도 메모장에 복사해둔다(롤백용).
2. **익명 로그인 켜기**: Firebase 콘솔 > Authentication > 시작하기 > 로그인 방법 > 익명 > 사용 설정.
3. **API 키 넣기**: 콘솔 > 프로젝트 설정 > 일반 > 웹 API 키를 `index.html`의 `FB_API_KEY`에 넣고 push. 이 키는 공개돼도 된다(접근 제어는 규칙이 한다). 키 사용 제한이 필요하면 Google Cloud 콘솔 > API 및 서비스 > 사용자 인증 정보에서 HTTP 리퍼러를 `hyonnie-t.github.io/*`로 제한한다.
4. **배포 확인**(1~2분 뒤): 사이트를 열고 개발자도구 Network 탭에서 `firebaseio.com` 요청에 `auth=`가 붙는지, 이전처럼 데이터가 뜨는지 본다. 이 시점엔 규칙이 아직 열려 있어 인증이 없어도 동작하므로 `auth=` 유무로 확인해야 한다.
5. **규칙 적용**: 콘솔 > Realtime Database > 규칙에 `database.rules.json`을 붙여넣고 게시 전에 규칙 시뮬레이터로 확인(인증 없음 읽기 → 거부, 인증 있음 읽기 → 허용).
6. **동작 확인**: 업무 등록·완료 체크·출석·공지가 되는지 본다. 막히면 5단계 전 규칙으로 되돌린다.

## 이 규칙이 막는 것 / 못 막는 것
- 막음: 주소만 아는 봇·외부인의 읽기·쓰기, 루트나 `tasks`·`events` 통째 삭제, `activity` 기록 수정·삭제, 정해진 경로 밖 쓰기, 일부 필드의 형식·길이 위반.
- 못 막음: 앱 코드를 읽고 익명 토큰을 받는 사람. 이 앱은 로그인 없이 이름만 고르는 구조라 한계가 있고, 개인정보를 이 DB에 넣지 않는 것이 전제다. 선생님 모드 비밀번호도 여전히 화면 수준의 확인이다.

## 규칙을 바꿀 때 주의
- 새 최상위 경로를 쓰는 기능을 만들면 규칙에도 추가해야 한다(없으면 쓰기가 거부된다).
- `tasks`·`events` 컬렉션 자체에는 쓰기 권한을 주지 않았다. 건별 키(`tasks/{id}`)만 쓸 수 있다 — 앱 전체 PUT 금지 원칙과 같은 방향이다.
